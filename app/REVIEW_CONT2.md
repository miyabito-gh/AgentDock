- 作成: 2026-10-23（設計担当）。対象: `app/PROPOSAL_CONT2.md`。背景: `app/DESIGN_CONT.md` §0・§1・§2・§4〜§6.2。コードは変更していない。
- 表記: 【事実】schema 0.163.0・設計書・コードで確認した。【推測】未確認（§5 の実機確認へ）。【前提】司令塔の案に「調査済み」とあり、本書では再確認していない。

## 0. 結論

1. **案は不採用（部分採用）**。①（目的メモの下書き）は採る。②は残す。**③（機械的圧縮）と④（語の重なり）は採らない**。業務用途では AI 返答の中ほど（議事録本文・メール下書き・集計表）こそ成果物で、③はそこを落とす。④は日本語で精度が出ず、外れたときに利用者から見えない。
2. 失念の主因は「圧縮の方式」ではなく、**引き継ぎのたびに新しい thread を作り、手元に原文の3往復しか渡さないこと**そのもの。直すべきは、(A) 引き継ぎを例外にして同じ thread を Codex の自動圧縮で長く使うこと、(B) 引き継ぐときは原文を捨てずに**ファイルとして渡し、Codex 自身に読ませる**こと。
3. 推奨は「A＋B＋①」の組合せ。モデル要約に頼るのは Codex 自前の圧縮と、利用者が確認する目的メモだけにする。

## 2. 案の評価（観点別）

**(1) Codex 自身の機能を使うべき場面**
- **同じ thread で続ける（最重要）**: 【前提】の圧縮仕様なら、利用者発言は約2万トークン分（日本語でおよそ2〜3万字【推測】）が原文で残り、AI 返答は要約で残る。現行の「3往復だけ」より明らかに多くを保つ。DESIGN_CONT の 70% 案内が引き継ぎを早く促しすぎて、かえって失念を増やしている可能性が高い【推測】。
- **compact_prompt の業務向け差替え**: thread 単位の `config` 上書きで渡せる形が schema にある【事実】。`~/.codex/config.toml` を書かずに済む（効くかは【推測】、K2）。指示例:「決定事項・数値・固有名詞・日付・未解決事項・成果物（下書き本文）の最新版を、往復番号つきで落とさず残す」。圧縮の弱点（AI 返答の消失）にそのまま効く。
- **developerInstructions**: thread 開始時の固定指示。目的メモの置き場所として最適候補。圧縮後も残る見込み【推測】。ただし途中で変えられるのは resume 時だけで、反映されるかは不明【推測】。現行の「圧縮観測後に目的メモを再添付」は保険として残す。
- **fork**: 文脈を減らさないので失念対策にはならない。「この時点から別案を試す」用途に留める。
- **revert**: 巨大ログを貼った往復などを履歴から外して文脈を空ける用途に使える。ただし破壊的なので、利用者の明示操作と確認ダイアログを必須にする。後回し。
- **Codex メモリ**: experimental。thread 横断・グローバルで、会話単位で制御できない。有効化は `~/.codex` 側の設定変更になる見込み【推測】で、合意に触れる。**採らない**（状態の表示だけなら可）。
- **inject_items**: 資料を利用者の本文に混ぜず、別の項目として入れられる。ただし Codex 固有の生の形式で、圧縮後に残るかも不明。第2段の候補に留める。

**(2) ファイルを長期記憶にする方式**
- 引き継ぎ時に、以前の thread の**全往復の原文**を AgentDock が `会話台帳.md`（往復番号・日時つき）として書き出す。資料には「目次（往復番号＋依頼の先頭1行）」と「全文は <パス>。必要な箇所は読んで確認すること」を入れる。Codex はエージェントなので、自分で検索して必要な部分を読める。これが④の上位互換になる（言い換えにも Codex の読解で対応できる）。
- 置き場所は AgentDock の管理領域（チャット領域）だけにする。開発チャットの cwd（利用者のリポジトリ）には書かない。sandbox から読めるかは【推測】（K4）。
- 「決定ログに Codex が追記する」方式は、毎回の追記指示がプロンプト追加になり、ファイル変更の承認も増える。代わりに①の目的メモを決定ログとして使う。利用者が押したときだけ下書きを作り、確認して保存する。これで足りる。

**(3) モデル要約の安全策**
- ①の下書きは、各項目に出典の往復番号（例 `[#12]`）を必須にする。出典のない項目は「出典なし」と表示する。利用者は確認・編集してから保存する。
- 原文は台帳ファイルと以前の thread に常に残す（DESIGN_CONT I2 で担保済み）。
- Codex の圧縮要約は読めない【事実】ので、利用者は確認できない。だから「要約は誤りうる、原文は台帳にある」という構造で受け止める。

**(4) ④の実効性**: 形態素解析なしの日本語では、語の境界が取れない。文字 bigram にすると「会議」「議事」のような雑音一致が多く、閾値の調整に終わりがない。言い換え（「見積」⇔「費用」）には効かない。**費用対効果は低い**。代替の比較:

| 方式 | 精度 | 実装 | 判定 |
|---|---|---|---|
| ④ 語の重なり | 低 | 中（閾値調整が続く） | × |
| SQLite FTS5（trigram） | 中（表記ゆれに弱い） | 中（依存追加） | 利用者向けの検索なら可。記憶用途には過剰 |
| 埋め込み | 高 | 大（外部 API かローカルモデル、費用） | × 個人用には過大 |
| **台帳ファイル＋Codex が自分で読む** | 高（モデルが判断） | 小 | **◎** |
| `thread/searchOccurrences` | 中 | 小 | 画面の検索用。experimental |

**(5) コスト・文脈消費**: 24,000字の日本語はおよそ16k〜24kトークン【推測：o200k 系で1字あたり0.7〜1トークン】。目的メモ4,000字で約3〜4k。窓が27万規模なら【推測。GPT-6.1-Sol の `modelContextWindow` は未確認】、新しい thread の約1割にあたる。つまり**24,000字の予算は窮屈すぎるわけではないが、③で削るほどでもない**。原文を捨てる理由は薄い。台帳方式なら、毎回入れるのは目次と直近の往復だけで済み、読む費用は必要なときにだけかかる。

**(6) 失敗時の挙動**: 要約の誤りは、出典番号と原文の台帳で検証できる。圧縮で情報が薄れたとき、つまり `contextCompaction` を観測した後の最初の手動送信には、目的メモ（既存）に**台帳・目次の場所を一行添える**。これで再注入の経路ができる。案の③は誤りを生まない代わりに欠落を生み、欠落は利用者から見えない。これが最大の欠点。

**(7) 合意との整合**: A（同じ thread）では、自動圧縮は Codex 本体の動作で、AgentDock が実行するものではない。compact/start は押したときだけ。compact_prompt は thread 単位の上書きで `~/.codex` を変えない（効くかは確認が要る）。B は AgentDock の領域に書くだけ。資料は利用者の手動送信の中でだけ付ける（I1）。監視目的の resume・プロンプト追加はしない。メモリ機能は有効化しない。未確認の表示については、圧縮後の要約を「保持済み」と表示しない（読めないため）。

## 3. 推奨方式と理由

**A. 同じ thread を既定にする**: 70% の案内を「引き継ぎ」から「圧縮されます。重要事項は目的メモへ」に変える。引き継ぎは、モデル変更・明示の新規開始・圧縮後の劣化を感じたときの手動操作にする。
**A'. 業務向けの compact_prompt**: 設定で opt-in し、文面を表示・編集できるようにする。thread の開始・再接続時に `config` で上書きする。
**B. 引き継ぎ資料の変更**: 目的メモ＋直近3〜5往復の原文＋全往復の目次＋台帳ファイルのパスと読む指示。③④は削除。
**①. 目的メモの下書き**: 押したときだけ1回。出典番号を必須にし、利用者が確認して保存する。

理由: 原文を捨てる処理がなくなる。検索は Codex に任せる。AgentDock 側は決定的で小さい純関数（台帳の書出し・目次）だけを持つ。

## 4. 段階的な実装順（最小で効く順）

1. **B-1 台帳と目次**（純関数＋ファイル書出し。現行の `continuity.rs` を小改修）。これだけで「3往復より前を失念」に直接効く。
2. **A 既定の変更**（文言と案内の切替。実装は小さい）。K1・K2 の結果を見てから。
3. **A' compact_prompt**（K2 で効果を確かめてから。設定1つ＋thread 開始時の上書き）。
4. **① 目的メモの下書き**（purpose_draft。出典番号・確認ダイアログ）。
5. 任意: 圧縮観測後の再添付に台帳の一行を足す／revert による文脈整理／`searchOccurrences` を画面の検索へ。

## 5. 実機で確かめること

- **K1 想起試験**（全体の判断材料）: 業務風の会話で、第3〜5往復に固有の数値・決定・人名を埋め込む。その後20往復ほど進めて質問し、(i) 現行の引き継ぎ、(ii) 同じ thread で自動圧縮1〜2回、(iii) B の台帳方式の三者で正答率を比べる。
- **K2** thread/start の `config: {"compact_prompt": …}` が効くか（圧縮後の回答の質、`config/read` の表示）。`~/.codex/config.toml` が変わらないことを前後照合する。
- **K3** GPT-6.1-Sol の `modelContextWindow`、日本語の文字数とトークン数の比（tokenUsage の差分で測る）、自動圧縮が始まる使用率。
- **K4** Codex が sandbox 下（一般・開発チャットの両方）で AgentDock 領域の台帳ファイルを読めるか。読むよう指示したときに実際に読むか。
- **K5** developerInstructions が圧縮後も効くか。resume で差し替えたときに反映されるか。
- **K6** 圧縮を繰り返したとき（要約の要約）に情報が劣化する速さ。
- 要判断: 圧縮要約の本文は `~/.codex/sessions` の rollout ファイルにある可能性がある【推測】。これを AgentDock が**読むだけ**で表示する場合、I6（`~/.codex` を読み書きしない）の例外にするか。推奨は「しない」（台帳で代替できる）。
