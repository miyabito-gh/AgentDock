## 1. 新規チャットの手軽な作成（クイック新規）

### 1.1 方式（推奨: 「下書きチャット」— 未決 Q1）

- 「クイック新規」はダイアログを開かず、中央に**下書きチャット**（まだ Codex の会話を作っていない入力画面）を出す。最初の送信で `startChat(firstMessage=本文)` を呼び、会話の作成と最初の依頼を1操作で行う。
  - 理由: 空の会話を作らない（発話前の会話は Codex に履歴が残らず、再起動後に「履歴なし」行になる既知の問題を増やさない）。押した瞬間に入力でき、待ち時間は送信後の進行表示（§2）に集約できる。
- 下書きチャットは App のメモリだけで持つ（1件。チャットではないので M40 の保存対象外。画面に「まだ作成していません」と出す）。チャットを選ぶと隠れ、もう一度クイック新規で戻る（文は残る）。
- 代替（Q1-B）: 押した瞬間に既定値で `startChat(firstMessage=null)` を呼び、空の会話を選択する。

### 1.2 既定値の決め方

| 項目 | 既定値 | 補足 |
|---|---|---|
| 作業フォルダ | **前回の作成で使った指定**（推奨。未決 Q2） | 新設 `AppSettings.lastNewChat`（§6）。一般チャットなら一般、開発チャットならプライマリ＋追加フォルダの並び。worktree を使った作成では、worktree の場所ではなく `WorktreeRecord.repoRoot` を記録する（クイックは worktree を作らない・結び付けない）。記録なし＝一般チャット |

| 権限 | 初期値（workspace-write＋on-request。`permission=null`） | ダイアログも権限を指定しないので「前回の権限」は常に初期値。§3.3「無断でフルアクセスにしない」に合わせ、後から変えたチャットの権限は持ち越さない |

- 記録の更新: ダイアログ・クイック新規・「同じ作業フォルダで新規」で**作成に成功したときだけ**更新する（失敗・受理不明では更新しない）。
- 強い確認・使えないフォルダ: クイックは `confirmedStrong=[]` で送る。ホストの再検査で拒否されたら（強い確認が要る・存在しない・追加フォルダ非対応）、作成せず、**同じ値と本文を入れた新規ダイアログ**を開いて理由を出す。強い確認をクイックで持ち越さない。

### 1.3 UI 配置

## 2. 作成中の無反応

### 2.1 遅い処理の内訳（コードで確認した事実）

順に直列で await され、その間 UI は何も出さない。

1. UI `Dialogs.tsx:485` `host.checkWorkFolder`（ファイル検査）。`creating=true` はここだけ。
2. **`Dialogs.tsx:495` の `finally{setCreating(false)}` が `onCreateChat` 呼出し前に走る**。以降の全処理中、作成ボタンは再び押せて表示も変わらない（二重押しで会話が2つできる不具合でもある）。
3. 「分離」時 `App.tsx:795` `host.createWorktree`（git worktree add。上限120秒）。
4. `App.tsx:804` `host.startChat` → ホスト `host/mod.rs:577` `start_chat`:
   - `verify_folder_set`（spawn_blocking でフォルダを再検査。ネットワーク上のパスは遅い）
   - **`thread/start`**（`codex/adapter.rs:787`、上限60秒。App Server 側の設定読込み・MCP 起動などで数秒かかる主因）
   - `bind_worktree_chat` → `save_worktrees`（ファイル書込みを await）
   - 最初の依頼があれば、**`thread/name/set`（名前付け RPC）を await → `dispatch_send`（送信前記録の保存・控えの取得・`turn/start` の受理まで）を await**（`host/mod.rs:681-709`）。
5. 戻ってからやっと `setDialog(null)`・選択。

結論: 主因は `thread/start`＋（最初の依頼ありなら）名前付け＋`turn/start` の3往復の直列待ちと、その間に UI が「作成中」を出していないこと。

### 2.2 即時フィードバック（UI）

- App に「作成中」一覧 `creating: CreatingChat[]` を持つ（純粋な reducer `ui/creating.ts`）。
  `CreatingChat = { tempId, label（最初の依頼の先頭 or フォルダ名 or「新しいチャット」）, startedAt, phase: "checking"|"worktree"|"starting"|"sending", result: null | {kind:"failed",message,retryInput} | {kind:"unknown",message} }`
- 押した直後:
  - ダイアログ: ボタンを無効化し「作成中…」＋スピナー。検査（1）が通ったらダイアログは閉じ、以後は一覧の仮行で示す（閉じても作成は続く。キャンセルで取消はしない＝取り消せない操作を取り消せるように見せない）。
  - 左一覧の先頭（並べ方によらず一覧の最上部、ピンより上）に仮行「作成中…（段階の文）」。選択・メニュー不可。
  - 下書きチャットから送ったときは、中央にも送信中の依頼（既存 PendingSend 表示）を出す。
- 結果:
  - 成功: 仮行を外し、実チャットを選択。`lastNewChat` を更新。
  - 失敗（ホストが拒否を返した）: 仮行を「作成できませんでした: 理由」に変え、「入力し直す…」（同じ値・本文でダイアログを開く。**自動で再送しない**）と「閉じる」を置く。
  - 不明（IPC エラー・タイムアウトなど、作られたか分からない）: 「作成を確認できません。一覧を更新して確認してください」＋「一覧を更新」。押し直しを促さない（二重作成の防止）。
- 二重押し: App 側でも `creatingRef` で同じ入力の多重呼出しを止める。別の新規作成（Ctrl+N 等）は別操作として受ける。

### 2.3 ホスト処理の非同期化（必要。理由: 仮行と実チャット行の二重表示を避け、作成後すぐ選択するため）

- `start_chat` は `thread/start` の応答と記録（`update_local`・`mutate`）までで返す。名前付けと最初の送信は `tokio::spawn` の後続タスクで行う（順序は従来どおり 名前付け→送信。挙動を変えない）。
- 戻り値 `StartChatResult.firstSend` は、後続タスクに渡す前に決めた**送信中（Sending）の試行**（attemptId 確定済み）を返す。確定は既存の `sendUpdated` イベントで届く（成功表示はイベントの受理だけ）。
  - `dispatch_send` に「試行IDを外から渡す」入口を足す（試行IDの採番を前に出すだけ。保存・照合の手順は変えない）。
  - 後着の順序: `sendUpdated`（確定）が IPC の戻りより先に届くことがある。UI は戻り値で仮の送信行を作るとき、`attempts[chatId]` に同じ attemptId の確定が既にあれば即反映する（純粋関数で）。
- 同じチャットへの重複送信の防止: 最初の送信が終わるまで、ホストはそのチャットの `send_message`／キュー自動送信を `Blocked{FirstSendInFlight}`「最初の依頼を送信しています」で止める（新しい BlockedReason。UI の `hasInFlight` に頼らない）。
- 受理不明・拒否・切断は既存の `dispatch_send` の扱いのまま（記録→照合、再送しない）。

## 4. 右ペインの複数タスクカード（A＋B）

### 4.1 今の原因（Dock.tsx）

- `Dock.tsx:222` 既定の「選択中」は `snap.chats.filter(c => c.key.id === selId)` で**選択中の1件だけ**。
- 「実行中」は `isWorkingForDock` で絞る（`Dock.tsx:222`）ため、完了した瞬間にそのチャットが集合から外れる。
- 「全」も `visibleOf` が完了・idle を `showFinished` 時だけ残し（`Dock.tsx:231`）、表示要素が空のチャットは `blocks` から落ちる（`Dock.tsx:234`）。→ 完了で消える。
- 入力欄はドックに無く、次の指示は中央でしか出せない。

### 4.2 構成

ドックの表示切替に「タスク」を足し、**初期値にする**（未決 Q4 で既存の3表示の扱いを決める。推奨: 「タスク｜選択中｜全」、「実行中」はタスクに吸収して廃止）。「タスク」は画面内の記憶（ホスト・MonitorScope は変えない）。

```
┌ dock-top（表示切替） ─────────────┐
├ 対応待ちの帯（sticky・最大でペインの50%、内部スクロール）┤
│  承認・質問のあるチャットのカード（要求を受けた古い順）     │
├ タスク（最近動かした順・最大5件。ペインごと縦スクロール）  ┤
│  実行中カード／終了カード                                   │
├ 「ほかのタスク N件」（1行表示の列。押すとそのカードを開く） ┤
└──────────────────────────────┘
```

- タスクの対象: アーカイブ済みでないチャット（作業中・対応待ちならアーカイブ済みでも）から、利用者が「閉じた」もの（署名が閉じた時から変わっていないもの）を除き、§3 の順に並べた先頭5件。6件目以降は「ほかのタスク」に1行で出す（消さない）。
- **完了しても消さない**: 状態が終わってもカードは残り、終了カードに変わる。消えるのは利用者の「閉じる」（×。画面内の記憶、新しい活動で再表示）・アーカイブ・削除だけ。
- 対応待ちの帯に入ったチャットは下のタスク列に重複して出さない。回答して要求が無くなれば帯から外れ、§3 の順の位置へ戻る。帯は5件の上限に数えない（承認・質問を隠さない）。

### 4.3 カードの中身

| 種類 | 条件（表示だけの規則。状態は書き換えない） | 中身 |
|---|---|---|
| 実行中カード | `isWorkingForDock`（親または子孫が作業中・対応待ち）。liveでない場合も状態は変換せず、鮮度の注記（既存 `FRESH`）を出す | 見出し（名前・状態チップ・開く・×）、子孫は `pickRecentDescendants` で直近3件（作業中・対応待ちを優先→最近の変化順）＋「ほかN件」（押すとカード内で全件。カード高さ上限＝ドック高さの約1/3、超過はカード内スクロール）、親の現在の活動1行、次の指示欄 |
| 終了カード | 上記以外（完了・失敗・中断・待機・状態不明） | 見出し、状態（状態不明・未確認失敗・履歴での確認は既存の文言のまま。「完了」と偽らない）、親の現在の活動（直近発言）を2〜3行（line-clamp）、次の指示欄。子孫は出さない。約120px |
| 帯のカード | 保留中の要求がある | 実行中カードの中身＋要求ごとに既存 `RequestCard`（CenterPane からそのまま使う。対象エージェント名・操作内容・選択肢と効力範囲） |

- 最新出力は `rootView.currentActivity.summary`（`Known`。未取得は「未確認」、非対応は「このAIでは非対応」）。カードのために履歴を読みに行かない。
- 次の指示欄（1〜3行の自動伸長）:
  - 下書きは中央と共有（`drafts[chatId]`・`onDraft`。M40 の保存もそのまま）。
  - 終了カード: 送信＝新しいturn。実行中カード: 「完了後に送る」（`host.enqueue`）。追加指示（steer）は中央だけ。
  - 送れない条件は理由を出して無効化: 送信前の添付がある（「添付は中央で送ってください」）、外部で作られ未再開（中央の再開確認が要る）、削除保留、送信の応答待ち（既存 `hasInFlight`）。
  - 送信結果は既存の PendingSend（受理不明は照合のみ、再送しない）をカードの下に1行で示す。
  - 送信処理は `onSend` を「対象チャットを引数で受ける」形に一般化して共用する（中央と同じ判定を通す）。
- 承認・質問のボタンは帯のカード内に直接置く（`onRespond` を共用。押した1件にだけ回答。帯の開閉・スクロール・カードの選択では回答しない）。
- 「開く」以外の操作（カードのクリック、表示切替）では中央の選択・送信先を変えない（§3.5）。

### 4.4 密度・高さ

- ドックの高さ・幅を ResizeObserver で測り、CSS 変数 `--dock-h` に入れる（実行中カードの上限 `max-height: calc(var(--dock-h) / 3)`）。
- 1行表示への自動切替（調整項目）: `cardDensity({dockH, dockW})` が `dockH < 520` または `dockW < 260`（一時パネルの狭い幅）なら `"line"`。1行表示は「状態チップ・名前・時刻」だけで、押したカード1件だけ展開する。帯のカードは1行表示でも要求の内容とボタンを省略しない。
- 定数（520 など）は `dockTasks.ts` に置き、後から調整できるようにする。

### 4.5 通知・入力中の扱い

- OS通知を押したとき（既存 `navigateToChat`）: 中央でそのチャットを開く（従来どおり）に加え、ドックが表示中ならそのカードへスクロールし、1行表示なら展開する。ドックが閉じている・一時パネルが閉じているときは開かない（D07: 通知でパネルを開かない）。
- 入力中は横取りしない: 中央の入力欄またはドックの指示欄にフォーカスがあり、変換中か文字が入っている間は、スクロール・展開・並べ替えをしない。代わりに対象カード（または帯の見出し）に印（●）を付け、フォーカスが外れたら印を残したまま位置だけ反映する。判定は `mayRedirect({focusInInput, composing, hasText})` の純粋関数。
- 帯の挿入で入力中の位置がずれないよう、ドックのスクロール領域は既定の scroll anchoring を有効のままにする（`overflow-anchor:none` を付けない）。

### 4.6 コンパクト監視窓

- 同じ「タスク」表示・並び・帯を使う（§3.5「同じ規則」）。ただし §3.11「承認・質問は通常の会話画面を開いて回答する」に従い、**監視窓のカードには回答ボタンと次の指示欄を出さない**（帯には要求の種類と「開く」だけ）。

## 5. 左ペイン折りたたみ時の幅（決定どおり）

### 5.1 判定（JS に一本化）

`paneWidth.ts` に純粋関数 `paneModes(i) -> { leftTemp, rightTemp }` を足す。`Lsaved = clampPane("left", 保存値)`。中央最小 480、ドック最小 260、左最小 180。

- 左を開いている（`leftOpen`）:
  - `leftSide = winW ≥ 480 + 180`（=660）
  - `rightSide = rightOpen && leftSide && winW − Lsaved ≥ 740`（左既定240なら 980px が境界）。左が一時パネルなら `winW ≥ 740`（実際は660未満なので false）。
  - 右が並置なら左の条件は `winW ≥ 920` になるが、`Lsaved ≥ 180` から上式で常に満たされる（矛盾しない）。
- 左を折りたたんでいる（幅0。レールなし）:
  - `rightSide = rightOpen && winW ≥ 740`
  - `leftTemp`（開こうとしたときの扱い）`= !(winW ≥ 660 + (rightSide ? 260 : 0))`。右が並置で窓幅が足りなければ、左は一時パネルとして開く（右を追い出さない）。
- 右を閉じている: `rightTemp`（開こうとしたときの扱い）`= !(winW − 左の表示幅 ≥ 740)`。
- `leftTemp = !leftSide`、`rightTemp = !rightSide` を、閉じているペインについては「開いたら並置できるか」で返す（`toggleLeft`／`toggleRight` が一時パネルか並置かを選ぶのに使う。既存の分岐のまま）。
- 幅が足りない間はドックを先に最小260まで縮め（既存 `displayWidths`）、それでも740に届かなければ一時パネル。左の保存幅は縮めない（決定の「1280→980」どおり）。
- 左の幅ドラッグは既存の `leftMax = winW − dock − 480` で上限が付くので、ドラッグで右が一時パネルに落ちることはない。
- 保存値（`AppSettings.layout`）は変えない。一時パネルの開閉は利用者の操作だけ（折りたたみ中に勝手にオーバーレイを開かない）。

### 5.2 CSS

- `.body` に `data-left-temp`／`data-right-temp`（真のときだけ属性を付ける）。グリッドは常に3列のまま、一時パネル側の幅変数を0にする:
