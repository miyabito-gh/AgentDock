# 組織実行 実機確認手順（段階1〜3・入口・空き容量）

対象: 組織実行の段階1（DESIGN_ORG_R1 §8）、入口（DESIGN_ORG_INTAKE §8）、段階2（DESIGN_ORG_R2 §10）、段階3（DESIGN_ORG_R3 §7・§9.3）、DEFERRED.md 2026-10-19 の空き容量項目。
作成: 2026-10-20。コードは変更していない。

凡例:
- `操作 → 期待` の形で書く。期待と違ったら、画面の文言とエラー全文を控える。
- ★ = 実機でしか確認できない点、または結果が未確定の点（Codex の振る舞いを含む）。
- ※ = 2026-10-19 に利用者が報告し、まだ直していない既知の問題（DEFERRED.md）。ここで再現すれば記録だけでよい。

## 0. 準備

```powershell
Set-Location "$env:USERPROFILE\Documents\AgentDockTest\repo-a"

git config user.name "Test User"

"# repo-a`n" | Out-File -Encoding utf8 README.md

git commit -m "init"
```

### 0-2 Gitでない業務フォルダを作る（入口・1の確認用）

```powershell
New-Item -ItemType Directory -Force "$env:USERPROFILE\Documents\AgentDockTest\business" | Out-Null
Set-Location "$env:USERPROFILE\Documents\AgentDockTest\business"
"議事録の下書き" | Out-File -Encoding utf8 memo.txt
```

- Excel（.xlsx）・Word（.docx）を1つずつ置く。
- 50MB を超えるファイルを1つ置く（例: `fsutil file createnew big.bin 52428800`）。
- `.git` は作らない（入口の「Gitを準備」を試すため）。

### 0-3 起動


- 方法B: 新しいインストーラーで導入する。★ インストーラーのビルドと配布先は、司令塔の確認手順（S 系）に従う。未作成なら方法Aで進める。
- codex.exe は `C:\Users\wmasa\AppData\Local\Programs\OpenAI\Codex\bin\codex.exe`（0.162.1）を設定で指定されていることを確認する。
- 既存の `~/.codex` の設定・認証は変更されない。

### 0-4 記録の取り方

- 項目ごとに 〇 / × / 未確認 を付ける。
- × のときは画面の文言・エラー全文・発生時刻・操作した順番を控える。
- 空き容量の項（10）は、エラー文の数値とドライブ名が必須。

## 1. 入口（依頼整理 → 要約確認 → 開始）

1. 依頼整理チャットで「議事録の要点をまとめる資料を作って」と話す → 「要約を作る」を押す → 要約カードに目的・成果物・未解決の点が埋まる。
2. 要約カードを編集 → 「開始」→ 確認ダイアログに依頼文が出る → 開始 → Planner の計画承認カードまで進む。
3. 依頼整理の途中、ワークフロー一覧に何も増えていないこと（開始を押すまで増えない）。
4. ★ 要約を作っている途中（turn 中）に App Server を止める（タスクマネージャーで codex を終了、またはネット切断）→ 「確認できません」と出る → 再送されない → 再接続後「履歴から読み直す」で要約が取り込める。
5. 長い依頼整理チャットを引き継ぎ（上限まで会話を進める、または引き継ぎ機能）→ 引き継ぎ後も要約カードの内容が残っている。
6. Gitでない `business` フォルダを作業フォルダにして「Gitを準備」→ `business` 直下に `.git` だけができる → 元のファイルは変わらない。
7. 除外: `ignored.tmp`・Office ファイル・50MB 超のファイルが、確認画面の除外一覧に出る → 一覧どおりに除外される（`git status` で追跡対象外になっていることを確認）。
   - `git -C "...\business" status` を実行し、除外したものが `??` に出ないことを確認する。
8. 初回コミットの作者: `git config user.name` を設定した状態（A）と、設定しない状態（B）の両方で確認 → 作者が利用者名（A）／AgentDock 名義（B）になる。
   - 設定を変えるときは `git config --global user.name` を使い、確認後に元へ戻す。
   - ★ 既存の `~/.codex` には触れないこと。
9. 準備を途中で失敗させる: `business` 内の1ファイルを読み取り専用にしてロックする、またはエクスプローラーで開いたままにする → 準備が失敗 → `.git` が消えて元に戻る（「元に戻しました」）。
   - 失敗表示のあと `business` に `.git` が残っていないこと。
10. プッシュ（★ 実GitHub。最後にまとめて行う）: `repo-a` で GitHub の個人リポジトリをリモートに設定 → 入口の「プッシュ…」→ 確認ダイアログ → 資格情報マネージャの画面が出て通る。
    - 未認証（資格情報を消して試す）→ 「認証に失敗」。
    - リモートを先に進めた状態（別クローンから push）→ 「先に進んでいます（pull が必要）」。
    - リモートなし → 案内のみ、実行されない。
    - ネット切断中 → 失敗表示。成功にならないこと。
    - 強制（force）の選択肢が出ないこと。

## 2. 進行の見える化（タイムライン・活動1行・塊）

1. ワークフローを開始（小さな依頼、例「README に一行追記して」）→ タイムラインに「計画」「作業」「検証」などが時系列で並ぶ。
2. 作業中、組織画面の「いまの動き」欄が1行で、役割ごとに「Worker: コマンド実行中」のような活動が出る。
3. ★ 3並列（Worker 同時2）のとき、「いまの動き」の文字が頻繁に入れ替わってチカチカしないこと。経過時間は進むこと。
4. 待ち・作業中・完了が塊（グループ）に分かれて見える。完了したタスクは畳まれ、待ちのタスクが上に出る。
5. ★ 接続を一時的に切る → 活動欄に「最新ではありません」の印が付く → 再接続後、印が消える。
6. 完了したワークフローのタイムラインに、コミットの行（「コミット abc1234」）が出る。

## 3. 承認・質問に答える／無反応時の表示

1. 承認が要るタスク（例: 「Worker に Web から最新の情報を取得させて」）→ 組織画面の注記行にカードが出る → 承認 → 作業が進む。
2. 左一覧・ドックに承認待ちの件数が出ていること（組織の行とバッジ）。
3. 承認待ちのまま App Server を再起動（またはネット切断）→ カードを押す → 「回答できません（接続が切り替わった）」と出る → 中断 → 「新しい試行で再送」で続く。
4. ※ 承認待ちのカードを押しても無反応だった場合（DEFERRED 2026-10-19 の1件目）: どの画面で見えたか（組織画面・役割チャット・ドック）、App Server の再起動があったか、を控える。画面に「承認待ち」の表示がなくても、エンジンは止まっているか（停滞通知が出るか）を見る。
5. ★ 承認待ちのまま停滞通知が出るまで放置 → 停滞通知が出ること（自動の中断はしないこと）。

## 4. 上限停止・失敗からの再開（再送上限）

※ 注意: DEFERRED 2026-10-19（2件目）によると、利用上限で止まったタスクの「再開…」が効かない既知の問題がある。下の1〜3は設計どおりかの確認であり、結果が設計と違えば記録して DEFERRED の該当項目へ回す。上限は再現できるときだけ確認する。

1. ★ 利用上限に当たったら（再現できるときだけ）: タスクの表示が「止まっています（利用上限）」、ワークフローの表示が「利用上限で停止中」になる（Failed にならない）。
2. 上限が解けたあと「再開…」→ チェックしたタスクが1回だけ送られる。送られたことがタイムラインに出る。
3. ★ turn の失敗（App Server 側のエラーなど）→ 「止まっています（turnが失敗）」→ 「新しい試行で再送」は利用者の操作1回で1回だけ送られる。自動では送られないこと。
4. 再送の上限（J-R3 の推奨既定は 3 回。設定値は実装どおりに確認）に達したら、上限到達が表示され、それ以上の再送が出ないこと。
5. 再起動後、上限・失敗で止まったタスクが「要対応」として見えること（Failed の終端扱いにならない）。

## 5. 介入（割り込み指示・追加指示・保留・スキップ・差し戻し・上限到達の3択）

### 5-1 割り込み指示（役割チャット）

1. Worker 実行中に役割チャットで「README にも一言追記して」と送る → 同じ turn の中で反映される → 最終回答が形式どおり → タイムラインに「届きました」。
2. ★ turn が終わる直前に割り込む → 「届きませんでした」と出る → 次の差し戻し・再送の turn に添えられる。
3. ★ 承認待ち中の turn に割り込んだときの挙動（steer が承認待ち中に受け付けられるか）を記録する。受け付けられた／拒否された／何も起きなかった、のいずれか。Codex の対応はここで確認する（要確認）。
4. 割り込み送信中に App Server を止める → 「確認できません」と出る → 自動では何も送られない → 再接続後の照合で決着する。

### 5-2 ワークフロー追加指示

1. 追加指示を2件入れる（例「用語は統一して」「見出しを3つまでに」）→ 実行中のタスクには入らない。
2. 次に始まるタスクの依頼文に、1回だけ入っていること（依頼文の表示または Worker の回答で確認）。
3. 計画承認待ちの状態で追加 → 承認カードに件数と「作り直し」が出る。

### 5-3 保留・スキップ・差し戻し

1. 未着手の Worker を「保留」→ 送られない。保留を解除すると進む。
2. 未着手の Worker を「スキップ」→ 対応する検証役も飛び、後続が進む。
3. Reviewer に2回差し戻させる → 「止まっています（差し戻し上限）」→ 次の3つの選択肢が出る（それぞれ試す。Failed にならないこと）:
   - 「もう一度直させる…」（文は必須・Worker が再度直す）
   - 「このまま受け入れる…」（検証不合格のまま受け入れ。表示「検証不合格のまま受け入れ」）
   - 「失敗として確定…」
   - 利用者の差し戻しは回数（自動の上限）に数えられないこと（記録のみ、表示で判断できなければ未確認）。
4. 完了済みの Worker を差し戻す操作は出ないことを確認する（設計 J-R2-3 の既定）。

### 5-4 停止の3項目（「止める…」）

1. 「新しい送信だけ止める」→ 実行中の作業は続き、次の送信だけ止まる。
2. 「実行中も止める」→ 実行中のタスクに中断が入る → 10 秒で「停止を確認できません」の案内（停止確定ではない）。止まったタスクは「新しい試行で再送」できる。
3. 「アーカイブ」（3項目目）→ ★ 作業中のアーカイブは未実装の可能性がある（末尾の一覧）。出ない／動かない場合は未実装として記録する。

## 6. 手動に切替 → 結果を取り込む

1. 実行中のタスクを「手動に切替」→ 役割チャットに入力できる。
2. チャットで続きを指示し、形式どおりの結果を出させる → 「結果を取り込む」→ タスクが完了 → コミット → 次のタスクが始まる。
3. ★ 形式外の回答（形式に合わない文章）→ 手動のまま戻る（完了にならない）。
4. ※ 手動切替後に成果物（スキーマ出力）が取り込まれない、またはエンジンが最終回答を読まない場合（DEFERRED 2026-10-19）は、その状態を記録する。
5. 手動のまま進めた後で「取消」→ 取消として扱われ、Failed や Cancelled の表示にならないこと（通信の問題ではなく利用者の操作として表示される）。

## 7. 成果物パネル → 取り込む → 戻す → プッシュ

1. 標準テンプレートで md・csv・画像・コードを作らせる（例「議事録の要約を md、一覧を csv、図を png、集計スクリプトを py で作って」）→ 完了後、成果物パネルにファイル一覧・行数・プレビュー・差分・Reviewer の所見が見える。
2. docx は「開く…」で Word が開く（プレビューは出ない）。
3. 「取り込む…」→ 確認一覧（ファイル・件数・衝突の有無）どおりに作業フォルダへ反映される。
4. `repo-a` の Git 履歴に取り込みコミットが1つ（候補ごと）できる（`git log --oneline`）。worktree とブランチは残る。
5. 作業フォルダで同じファイルを未コミットで編集してから取り込む → 何も変わらず、重なったファイルが示される。
6. 別のファイルの未コミット編集だけなら取り込め、その編集は残る。
7. ★ 取り込み対象の xlsx を Excel で開いたまま取り込む → 「開かれています」で止まる。閉じて再試行すると取り込める。ウイルス対策による一時的なロックで止まった場合は閉じ直して再試行する。
8. 自分のブランチで同じ行を先に変更・コミットしてから取り込む → 衝突の案内が出て、作業フォルダは変わらない。
9. 取り込み後「取り込み前に戻す」→ 元に戻り、候補が再び「レビュー待ち」になる。
10. 取り込み → 「プッシュ…」 → 送信後は「戻す」が無効になる（押せない）。
11. 取り込みの対象が、入口で作ったリポジトリ以外の「サブフォルダ」（R3 §9.3）のときも、重なり検査と取り込みが同じように働く。
12. 再起動後、パネルの所見・取り込み済みの印が残る。
13. 候補のファイルを成果物パネルから削除できないこと（削除はワークフローの「削除…」のみ）。

## 8. 一時停止の3分類

1. 「新しい送信だけ止める」→ 新しい送信が止まり、実行中は続く。表示は「一時停止中（新しい送信だけ）」など区別できること。
2. 「実行中も止める」→ 実行中のタスクが止まり、10 秒で停止未確認の案内。停止を確認できないまま削除しない。
3. 「アーカイブ」（作業中のアーカイブ）→ ★ 一覧から隠れるだけで、作業・通知は続く。未実装なら末尾の一覧に従う。
4. 再開は、それぞれ対応するボタンで戻ること（停止した種類ごとに、戻る操作が違うか確認する）。

## 9. 削除・アーカイブ（組織ワークフロー）

1. 完了したワークフローの「削除…」→ 確認の削除プレビューが出る（未マージ数・worktree・ブランチの扱い）。
2. 取り込み済みの候補がある場合、削除プレビューの未マージ数が 0 件として表示される（DESIGN_ORG_R3 の冒頭5項の設計どおり）。
3. 削除を確認 → ワークフローが一覧から消え、記録（`org\<wf>`、`imports.jsonl` を含む）が消える。
4. 削除しても `repo-a` の worktree とブランチは自動では消えない（削除プレビューの選択に従う）。ブランチを消すかどうかは利用者が選ぶ。
5. 削除後、Codex の履歴（既存の会話）は残ること。
6. ★ 停止未確認・実行中のワークフローを削除しようとしたとき、どう止まるか（削除が拒否される・案内が出る）を記録する。
