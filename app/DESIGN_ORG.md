## 1. AgentDock側との境界

### 1.1 エンジンの配置【決定 Q1】

- 別crate `org-engine`（`app/org-engine/`、Tauri・Codexに依存しない純Rust。ホストからpath依存）をホストのプロセス内で動かす。Codexへはホストの `AiBackend` 経由で、App Serverは既存の1つを共有する。
- 理由: 承認・質問UI、子孫監視、Job Object、停止照合、送信条件、通知、保存がそのまま使え、同じthreadを2つの接続で扱わない。まとめ §3 の「論理的・実装上独立」はcrate境界で満たす。
- エンジンとホストの間は**直列化可能なメッセージ（`OrgCommand`／`OrgEvent`）とポートtrait**だけにする。将来別プロセスへ移すときにcrate内部を変えない。
- panic対策【設計】: エンジンは専用のtokioタスクで動かし、境界で `catch_unwind` してエンジンだけを「停止（内部エラー）」にする。ホスト・既存チャットは継続。

### 1.2 ポート【設計】

エンジンはCodexを知らない。ホストが次のポートを実装する（中立型のみ。`ChatKey`＝バックエンド種別＋内部ID、正本 §2.3）。

|ポート|役割|ホスト側の実装|
|---|---|---|
|`AgentRuntime`|役割チャットの作成（cwd・sandbox・モデル・effort・指示）、タスク送信、利用者操作による停止、履歴read|`AiBackend::start_chat`／`send`／`interrupt`／`read`。送信の受理不明は既存の `SendOutcome::Unknown` をそのまま返す|
|`RuntimeEvents`|turn終端・子孫状態・鮮度・承認待ちの発生／解消を受ける|既存の `BackendEvent`→正規化状態を、所有記録（§1.4）で絞って流す|
|`Workspace`|worktree作成、所有worktree内のコミット、コミット間差分|`gitops/`（追加関数は §3.1）|
|`OrgStore`|状態・イベントの永続化|`store/` 配下（§3.4）|
|`Clock`／`Notifier`|時刻、通知要求|既存 `win/clock`・`host/notifier`|

### 1.3 既存合意との線引き【決定から導出】

|既存合意|衝突の可能性|線引き|
|---|---|---|
|監視目的でresume・プロンプト追加・停止をしない（M11）|エンジンは能動的にプロンプトを送る|**組織実行は監視とは別経路**。送信できるのはスケジューラが `ready` にしたタスクだけ。権限は利用者がワークフローを開始したときに発行する `OrgGrant`（ワークフロー単位、一時停止・停止・終了・再起動で失効）に紐づける。監視・表示・照合・再起動処理のコードは `OrgGrant` を持たない（型で強制）。resume は利用者の「ワークフローを再開」操作の中でだけ行う（U1 確定。組織の自動送信は live 必須で、live でなければ送らず止める。DESIGN_ORG_P4 D6）|
|承認代行をしない|条件付き自動承認（決定4）|自動承認は**エンジン内の計画承認だけ**。Codexのサーバー要求（command・fileChange・permissions・requestUserInput・elicitation）にエンジンは応答しない。既存の承認カードで利用者が答える。待つ間タスクは `running`＋待機理由（§4.1のwaiting）|
|権限を無断で広げない（§3.3）|役割定義で承認回避・フルアクセスにできてしまう|役割の権限は既定（workspace-write＋on-request）以下へ**狭める方向だけ**。広げる定義は読込み時に無効のまま理由を表示し、利用者の明示有効化を要する（自動承認の判定外＝常に利用者確認）|
|無条件再送しない／受理不明は照合|ディスパッチの受理不明|確認状態「送信受理不明」（§4.1）に入り、スケジューラは触らない。readで照合し、turnが見つかれば `running`、見つからなければ利用者に「送る／取り消す」を出す|
|失敗・中断した依頼を自動再実行しない（§3.7）|差し戻し|差し戻しは**レビュー結果を根拠とする新しい指示**で再実行ではない。上限内（Q5）で自動。Codex実行自体の失敗（turn failed・systemError・利用上限）は再送しない→ `failed{実行失敗}` で利用者へ|
|通信断・取得不能をdone/failedにしない|業務タスクの完了判定|業務完了は「liveでturn終端（完了）」＋「子孫に作業中なし」＋「成果物の検証合格」の全部。切断・wake・再起動は確認状態「要照合」へ。履歴で終端を確認しても成果物を検証するまで `completed` にしない|
|強制終了はJob Object・管理外は対象外|エンジンのthread|エンジンのthreadは既存App Server上にあり既存の強制終了の対象に入る。確認画面に「組織実行中のタスク」を併記。`KILL_ON_JOB_CLOSE` を付けない方針は維持（異常終了で作業を止めない）→再起動時に要照合|
|起動だけで過去の依頼・キューを再実行しない（§3.11）|決定2「次回起動時に照合・復旧」|照合は自動（readのみ）、ディスパッチ再開は利用者の「ワークフローを再開」だけ（Q8）|
|監視・要約のための追加モデル呼出をしない（§6）|Planner等の呼出し|組織実行の呼出しは利用者が開始した作業そのもの。監視・表示の要約には使わない|
|`~/.codex` を無断変更しない|役割定義・状態の保存先|AgentDockの専用領域に置く。Codexの設定・カスタムエージェント定義は読まない・書かない|

### 1.4 所有と既存機能の挙動【決定 Q9＋設計】

- エンジンが作ったチャットは `chat.json` に `org: { workflowId, taskId, roleId }`（追加フィールド、`#[serde(default)]`）を持つ。所有はこの記録だけで判定し、推定しない。
- 組織チャットへの通常送信・追加指示・完了後キューは無効（理由「組織実行中。介入はワークフロー画面から」）。
- 介入は手動切替に加えて、割り込み指示（steer）と追加指示（次の turn に添える）。turn の開始はエンジンだけ（2026-10-19 変更、`DESIGN_ORG_R2.md`、Q9 変更）。「このタスクを手動に切り替える」を押すとタスクは `blocked{手動}`、`OrgGrant` からそのチャットを外し、以後は通常チャットとして送信できる。エンジンはこのタスクへ二度と送らない。戻す操作は「手動の結果を受け入れて完了」（成果物の検証を通す）か「取り消す」。
- 中断ボタンは使える（利用者の明示操作）。結果はタスクの確認状態「中断要求済み」→終端確認で `blocked{手動停止}`。
- 組織チャットの削除・アーカイブはワークフロー単位でだけ行い、既存の停止確認・削除保留に従う。

## 3. 既存機能の流用

### 3.1 worktree（§3.14 #14）【設計】
- Workerは1タスク1worktree。置き場所は合意どおり `%LOCALAPPDATA%\com.agentdock.app\worktrees\`、ブランチは `agentdock/org/<wfShort>/<taskId>`。`worktrees.json` の `WorktreeRecord` に `org` 所有を追加。
- Reviewerはread-only sandboxで、対象コミットを固定した**読取り用worktree**（detached HEAD）を使う。
- `gitops/` に3関数を追加（任意のgitコマンドは受け付けない方針を維持）: `commit_all_in_owned_worktree`（AgentDock所有のworktreeだけ。利用者のブランチ・作業ツリーでは拒否）、`add_detached_worktree`、`diff_commits`。
- Workerのturn完了後、エンジンがそのworktreeをコミット（コミット作者はAgentDock）し、レビューはそのコミットを対象にする。
- 統合は自動で行わない（Q7、§4.6）。worktreeの削除は既存規則（未コミット変更があれば止める、`--force`は2段目の確認、ブランチは残す）。ワークフロー削除でも自動では消さない。

### 3.2 キュー（§3.7）
- エンジンのタスク待ち行列はチャットのキューとは別物。キューの実装は流用しない。
- 流用するのは**送信条件の判定**（`rules/queue.rs`: 親live必須、子孫は終端確認、2026-10-12合意の「親live完了なら状態不明の子は注記して進める」）と、送信前の `PendingOp` 保存・受理不明照合。

### 3.3 通知集約（§3.11）
- `rules/notify.rs` の2秒固定窓をワークフロー単位のキーで使う。承認・計画承認・停止系は即時。起動時の一斉通知をしない規則も同じ。

### 3.4 保存層【決定 Q6】
- 置き場所: `%LOCALAPPDATA%\com.agentdock.app\org\<workflowId>\`。期限なし・容量不足で自動削除しない。使用量に「組織実行」の行を追加。
- 方式: `workflow.json`（スナップショット、`store/atomic.rs` で原子的に書換え）＋`events.jsonl`（追記、全状態遷移を1行1イベント、各行に `schemaVersion`）。再起動時はスナップショット＋後続イベントで復元し、末尾の壊れた1行は捨てて記録する。
- `OrgStore` traitで隠し、後からSQLite等へ替えられるようにする。新しいネイティブ依存は追加しない。
- 役割定義: `org\roles\*.json`（§4.2）。
- 正本の位置付け: 組織の状態（タスク・依存・承認・差し戻し）は**エンジン保存が正本**、会話本文はCodexの履歴が正本。

### 3.5 終了確認・停止照合（§3.4）【決定2から導出】
- 完全終了の手順にエンジンを前置する: ①スケジューラ停止（新規ディスパッチ禁止、`OrgGrant` 失効）→②状態保存→③既存の停止手順（送信保留→中断→再発見→停止照合）→④各タスクを `cancelled` にせず、確認状態「中断要求済み」または「停止未確認」で保存→⑤終了。
- 10秒で停止未確認の案内、強制終了は既存のまま。強制終了後も「停止未確認」（まとめ §2.1「中断失敗・強制終了時の扱い」への回答）。
- 中断時点のファイル変更は破棄しない。worktreeに残し、次回のタスク表に「未コミットの変更あり」と出す。

## 4. 設計項目5以降（確定内容）

### 4.1 タスク状態（まとめ §4.2 の拡張）【設計】

業務状態と**確認状態**を別軸にする（正本 §4.1／4.2 の分離と同型）。

|軸|値|
|---|---|
|業務状態|`pending`／`ready`／`running`／`blocked{承認待ち｜手動｜手動停止｜上限｜要対応}`／`reviewing`／`rework`／`completed`／`failed{実行失敗｜成果物不正｜上限到達}`／`cancelled`|
|確認状態|`確定`／`送信受理不明`／`要照合{切断｜wake｜再起動}`／`中断要求済み`／`停止未確認`|

- 確認状態が `確定` 以外のタスクにスケジューラは何もしない。それに依存するタスクも進めない。独立なタスクは進められる（まとめ §2.2）。
- `cancelled` は利用者の取消か、停止を確認できたときだけ。終了・強制終了・通信断で `cancelled`／`failed` にしない。
- 単体テスト対象（純粋ロジック）: 状態遷移表（全許可遷移と禁止遷移）、DAG検証、ready集合、確認状態による停止、ポリシー判定、差し戻し・再計画・turnの回数。

### 4.2 エージェント構成（設計項目5）【決定 Q2】
- 定義ファイルによる拡張型。標準役割は Planner・Worker・Reviewer（テストはWorkerの完了条件とReviewerの検証項目に含める。Tester役は後で定義ファイルで追加可能）。
- 定義ファイル `org\roles\<id>.json` の項目: `id`・表示名・モデル（不透明ID。未指定＝チャット既定）・effort・指示テンプレート・sandbox（`readOnly`｜`workspaceWrite`）・承認方針（既定以下のみ）・作業場所（`sharedReadOnly`｜`ownWorktree`｜`detachedAtCommit`）・出力スキーマID・同時実行上限。
- 標準3役の定義ファイルは初回起動時に作成する（既存ファイルは上書きしない）。
- Plannerは**既存の役割IDから選ぶだけ**。未知の役割を含む計画は形式検証で不合格。
- 権限を広げる定義は §1.3 のとおり無効のまま読み込み、理由を表示。

### 4.3 計画の検証と自動承認条件【決定 Q3】
- Planner出力は構造化JSON。`turn/start` の `outputSchema` を使う（採用確定。実測: 最終agentMessage 1件がスキーマ準拠JSONで返り、依頼文がスキーマに反してもスキーマが優先された。スキーマは後続turnに残らないので**毎turn指定する**。§5.4）。それでも解析・検証に失敗したら1回だけ形式修正を依頼し、それも失敗なら利用者へ（自動で繰り返さない）。
- **形式検証**（常に必須。不合格は承認以前に差し戻し）: DAG（循環なし）・既知の役割・依存の実在・タスク数上限（初期20）・各タスクの宣言効果 `effects`。
- **常に利用者確認**（これ以外は自動承認）:
  1. 効果に「利用者の作業ツリー・ブランチへの書込み」「push・マージ・タグ」「作業フォルダ外」「ネットワーク取得・パッケージ導入」「秘密情報・認証」「削除を主目的とする」を含む
  2. 有効化されていない役割（権限を広げる定義）を使う
  3. 再計画で目的・対象範囲が変わる、または自動再計画の回数（1回）を超える
  4. タスク数・並列数・turn上限を超える
- 効果宣言はAIの自己申告なので、**強制は sandbox と cwd（worktree）で行う**。自己申告は「確認を求める理由」にだけ使い、自動承認の唯一の根拠にしない（決定4）。

### 4.4 並列数・リソース【決定 Q4】
- Worker同時2・全体の同時実行タスク3（設定で1〜4。ワークフロー画面に表示）。
- 利用上限・レート制限を示すイベントや失敗を観測したらスケジューラを一時停止（`blocked{要対応}`）し、自動で再試行しない。

### 4.5 依存・再計画・差し戻し上限【決定 Q5】
- 差し戻しはタスクごとに2回（試行3回）まで自動。超えたら `failed{上限到達}` で利用者へ。
- 自動の再計画は1ワークフローにつき1回。2回目以降と、範囲が変わる再計画は利用者確認（§4.3の3）。
- レビュー対象の陳腐化: 依存先が再実行で新しいコミットになったら、後続のレビュー結果を「陳腐化」と示し `rework` 候補にする（`completed` を自動で取り消さない）。

### 4.6 統合【決定 Q7】
- 自動マージしない。ワークフロー完了時に、タスクごとのブランチ・コミット・差分（既存の差分表示）を示す。取込みは利用者がGitで行う（AgentDockは取込み操作を持たない。MVP範囲）。

### 4.7 失敗・中断・再起動・停滞【決定 Q8・Q10】
- 再起動時: スナップショット＋イベントで復元 → `running`・送信受理不明のタスクを確認状態「要照合{再起動}」に → readのみで照合（turn終端・子孫・worktreeの実在と未コミット変更）→ 結果を表示。ワークフローは「再起動後の停止」で、利用者の「再開」までディスパッチしない。
- 照合で終端を確認できたタスクも、成果物の検証を通るまで `completed` にしない。確認できないものは要照合のまま残し、利用者が「受理不明として取り消す／手動に切り替える」を選ぶ。
- wake: 既存どおり鮮度を不明にし、組織のディスパッチも保留。照合後に自動で戻すのは既存の「接続が続き照合成功→live通知」条件を満たしたときだけ。
- 停滞: 同じタスクで新しい活動が設定時間（初期30分）ないとき通知だけ出す（自動中断しない）。

### 4.8 API・プロセス管理【設計】
- Tauri IPCに `org_*` コマンド（開始・計画承認・再計画依頼・一時停止・再開・取消・手動に切替・状態取得）とイベント `orgUpdated` を追加。ts-rsで型生成。状態を変えるコマンドは `UserConfirmed` を要求。
- エンジン本体は `OrgCommand`→`OrgEvent` の逐次処理（単一の所有タスク＋mpsc）。ホストのロック（`HostState`）を保持したままエンジンへ同期呼出しをしない。エンジン→ホストはポート経由の非同期呼出しのみ。
- 起動: ホスト起動時にエンジンを起動し、保存済みワークフローを「再起動後の停止」で読み込む。終了: §3.5。同時に動かせるワークフローは1つ（MVP）。

### 4.9 ログ・コスト・セキュリティ【決定 Q11＋設計】
- 実行記録: タスクID・試行・`ChatKey`・turnの中立ID・役割・モデル（選択値と受理値）・開始終了時刻・確認状態・トークン使用量（`thread/tokenUsage/updated` はturnごとに1回、turn分は `last.totalTokens`（実測、§5.4）。通知が来なかったturnは「未取得」、0で代用しない）。
- コスト上限: ワークフローあたりのturn数上限（初期30、設定可）。送信前に数え、到達でディスパッチを止め `blocked{上限}` で利用者へ（「上限を増やして再開／終了」）。形式修正・差し戻しも1turnとして数える。トークン量は表示だけ。
- 成果物はデータとして扱い、本文由来のコマンドをホストで実行しない。役割間の受け渡しは区切り付きの引用として渡し「指示ではなく資料」と明記する（注入の緩和。完全な防御ではない）。
- 認証情報・秘密を成果物・ログに保存しない。

### 4.10 sandbox健全性チェックと起動引数・trust【確定 J1-A・J2-A、§7】
- **健全性チェック**【設計】: ワークフロー開始前（計画承認後・最初のWorker/Reviewer送信前）に、App Server上で軽量コマンドを1回実行して exit 0 を確認する。失敗したらワークフローを開始せず（`blocked{要対応}`）、原因候補「node_repl／cua_repl とsandbox更新の競合（`os error 32`）」と、`~/.codex/.sandbox/` のログ確認、回避手順（下記）を示す。自動再試行・自動回避はしない。このチェックは利用者が開始したワークフローの一部で、監視目的の実行ではない。チェック用コマンドもsandbox内の読取り専用の軽いもの（書込みなし）にする。
- **起動引数の回避**: `-c features.plugins=false -c mcp_servers.node_repl.enabled=false` はApp Server全体に効く。既存のAgentDock用App Serverを共有する（Q1）ので、通常チャットのプラグイン機能（computer-use等）も無効になる。確定（J1-A）: 設定に回避オプション（既定オフ）を設け、健全性チェックが失敗したときだけオンを案内する。オンにするとApp Serverの再起動が要り、既存の完全終了／停止確認の手順に従う（実行中の作業があれば止めない）。`mcp_servers.cua_repl.*` は渡さない。`~/.codex` は変更しない。
- **thread単位の上書きの可否（要検証、P-ORG-4）**: `thread/start` の `config` 等で組織実行のthreadだけ無効にできるなら、それが副作用最小。未検証のため本書は前提にしない。
- **trustエントリ**: AgentDockは `config.toml` を書かない。Codex本体の追記は許容し、既存の前後照合（正本 §13.3）で `[projects.'<cwd>']` の `trust_level` 追加だけの差分を「Codex本体の自動追記」として区別表示する（変更として警告しない・自動rollbackしない）。それ以外の差分は従来どおり扱う。増加を抑える案として、trust済みの共通親フォルダ配下にworktreeを置けばエントリが増えないかを P-ORG-4 で検証する（P-ORG-4で検証する。置き場所は `%LOCALAPPDATA%\com.agentdock.app\worktrees\` の合意を維持し、変更が要る結果になれば改めて報告する）。確定（J2-A）。

### 5.4 実測（2026-10-17、codex 0.162.1、model gpt-6.1-sol、P-ORG-1）

実行は `probes/app-server/org-probe.mjs`。全回で `configUnchanged`／`authUnchanged` とも true。

- **項目1 outputSchema（確定）**: 準拠する依頼で最終agentMessage 1件が `{"answer":2,"unit":"none"}`（JSONとして解析でき型も合致）。スキーマに反する依頼でもスキーマ準拠JSONが返った（スキーマが優先）。次のturnでoutputSchemaを付けないと `ok`（プレーン文）で、スキーマは後続turnに残らない。→ 採用確定、毎turn指定（§4.3）。
- **項目2 read-only sandbox＋worktree cwd（確定）**: 初回（回避なし）は、turn内の全コマンドが `status: failed, exitCode: -1`（`Failed to create unified exec process: helper_unknown_error: setup refresh had errors`）。原因は §5.5 のsandbox競合で、worktree固有ではなかった。回避を付けて再測定（ユーザー実機、`org-probe.mjs 2b --no-plugins`）した結果:
  - (a) 通常フォルダ read-only: 読取り成功（exit 0、内容取得）、書込みは read-only 制限で失敗。
  - (b) worktreeをcwdにした read-only: 同上（読取り成功、書込みは「アクセス拒否」exit 1、ファイル未作成、worktree statusは空）。**worktree固有の問題なし**。
  - (c) worktree＋workspace-write: 読取りも書込みも成功（`?? write_c.txt` が現れる）。
  - 全ケースで server request 0件（approvalPolicy=never では承認要求が出ない）。
  - 結論: Reviewer等の読取り役割は read-only＋detached worktree で成立する。ただし sandbox が起動できる環境が前提（§4.10 の健全性チェック）。
- **項目3 並列3thread（確定）**: 同一App Serverで3thread並行、wall 2950ms（各turn 2.5〜2.9秒、合計8211ms）、全て完了、取り違えなし。→ 並行可（§4.4）。
- **項目4 tokenUsage（確定）**: `thread/tokenUsage/updated` は1 turnにつき1回（turn完了付近）。`total` はthread累積、`last` はそのturn分（2turn目: total=34872=17424+17448、last=17448）。`modelContextWindow`=475000。内訳は inputTokens／cachedInputTokens／cacheWriteInputTokens／outputTokens／reasoningOutputTokens／totalTokens。→ turn単位の使用量は `last.totalTokens`。1 turnあたり約1.7万トークンのベースライン（システムプロンプト等）がある点をコスト見積りで考慮する。

### 5.5 環境上の発見（2026-10-17、P-ORG-1。設計への反映は §4.10）

- **sandbox起動失敗**: この環境で App Server を自分で起動して `thread/start` すると、全コマンドが `Failed to create unified exec process: helper_unknown_error: setup refresh had errors` で失敗した。`codex sandbox` 単体は成功し、Codex公式アプリ自体のチャットは動いた。
- **原因**: `thread/start` で `node_repl`（config.toml の `[mcp_servers.node_repl]`）と `cua_repl`（プラグイン unified-computer-use の `.mcp.json` 由来）が起動する。`~/.codex/.sandbox/` のログでは、sandboxのセットアップ更新が `runtimes\cua_node\...\node_repl.exe` のACL更新で `os error 32`（別プロセスが使用中）になっていた。
- **回避（検証済み: モデル呼び出しなしの確認＋2b）**: App Server の起動引数に `-c features.plugins=false -c mcp_servers.node_repl.enabled=false`（`~/.codex` は変更しない）。効かなかったもの: `node_repl` だけの無効化、プラグイン個別の無効化、`features.computer_use` 等の無効化。`mcp_servers.cua_repl.*` を渡すと未定義名で "invalid transport" となり App Server が起動時に落ちる（**渡さない**）。
- **副作用**: `features.plugins=false` は computer-use 等のプラグインを使うチャット機能を無効にする。
- **trust自動追記**: Codex は新しい cwd で thread を作ると `~/.codex/config.toml` に `[projects.'<cwd>'] trust_level = "trusted"` を自動追記する（プローブで3回観測）。AgentDock が書いたのではなく Codex本体の動作。組織実行が worktree ごとに cwd を変えると増え続ける可能性がある。
- 注: 通常チャットが承認を挟んで動いていたのは、sandbox失敗で昇格を求められていた可能性がある（未検証）。
