## 1. 調査の前提と現状

AgentDock側は文書だけでなく現在のコードを確認した。他製品は公式ドキュメント・公開UI説明に基づき、実アプリを操作して検証したものではない。外部仕様の確認日は上記作成日。提供状況や画面配置は今後変わり得る。

現在のAgentDockは「表示された要素を選んでAIにコード修正を依頼し、編集用コピーを確認して元へ反映する」仕組み。

| 項目 | コードで確認した現状 |
| --- | --- |
| 配置 | 中央に既存チャット、右に編集状態・操作とHTMLプレビュー。右ペインの幅を変更可能 |
| 選択 | クリック、ドラッグ範囲、Ctrlで追加、親要素へ拡張、解除 |
| 動作確認 | 範囲選択／ページ操作を切替。ページ操作ではリンク・ボタンなどを操作 |
| AI依頼 | 編集チャットへの送信に選択情報を自動添付。選択なしでも依頼可能 |
| 指示のひな形 | 色・サイズ・配置・テキスト・レイアウト。設定値を直接変更するコントロールではない |
| 編集対象 | HTML・CSS・JS・MJS・SVGを編集可として収集。画像・フォント・JSON等は表示専用 |
| 会話 | 今の会話／分岐／新しい会話で開始する経路を実装 |
| 確認・反映 | ファイル本文の変更前後、直前のAI編集の取り消し、利用者操作による元への反映 |
| 未実装 | 製品機能としての文字直接編集、色・サイズ・余白の設定パネル、選択箇所付近の依頼入力、共同編集 |

選択範囲はAIへの目安で、範囲外の変更を禁止する境界ではない。現行送信文は必要なら範囲外も修正してよいと伝える。「ここだけ変更」を保証するUIとして扱わない。

「直前の編集を取り消す」はコピー上のAI編集の復元。元への反映後に元ファイルを反映前へ戻すUIは未実装。保存バックアップの存在と、製品の復元操作を区別する。

## 2. ChatGPT Slidesとの比較

Slidesは「利用者が画面上で直接編集し、AIにも修正を依頼できる」構成。Web・デスクトップでは文字・画像・図形・表・グラフを直接編集し、要素選択からRequest edits、全体にはプロンプト欄を使う。同時編集、共有コメント、AIへのメンション、発表・出力も提供する。[公式ガイド](https://learn.chatgpt.com/docs/space/getting-started)

| 観点 | AgentDock現行 | Slides |
| --- | --- | --- |
| 小さな修正 | 選択後、中央チャットで依頼しAIの完了を待つ | 要素を直接編集できる |
| AIへの部分依頼 | 選択情報をチャットへ添付 | 選択要素からRequest edits |
| 全体の変更 | 通常チャットで依頼 | プロンプト欄で依頼 |
| 対象 | ローカルHTMLと関連ファイル | プレゼンテーションの要素 |
| 確定 | コピーを確認し元へ反映 | 同じデッキを編集していく |
| 確認 | ファイル本文の比較 | 編集面で内容を確認、発表・出力 |

Slidesの細かなスタイル設定、取り消し・履歴、ペイン幅の仕様は今回未確認。「Request editsの入力欄が必ず選択要素のすぐ隣に出る」とは確認していない。以下の近傍入力はAgentDockへの改善提案。

## 4. 追加機能と推奨方式（提案・未実装）

### 選択箇所の近くからAIへ依頼

現行は「右のページで選択→中央の入力欄に移動→送信」。提案は「選択→付近のAIに依頼ボタン→小さな入力欄から送信」。AIの能力より、視線と操作の移動を減らす変更。

送信は既存チャットの経路を再利用し、履歴・送信ガード・受理不明の処理を維持する。短い修正はその場、長い相談は中央チャットで続ける。選択付近へ置くかプレビューの固定位置にするかは、遮蔽・入力・スクロール追従を試して判断する。

### 文字・色・サイズ・余白

候補方式は2つ。

| 方式 | 使い方 | 主な課題 |
| --- | --- | --- |
| 一時プレビュー＋AI保存（初期推奨） | 操作中はDOMへ仮適用し、適用時に変更値・指示をAIへ渡してコピーのソースを修正 | 仮表示とAIの最終結果は一致保証がない。結果の確認が必要。仮編集とAI編集中の競合管理 |
| 直接ソース保存＋難しい変更だけAI | 単純な文字・スタイル変更を確定的に保存 | DOMとソースの対応、CSSの適用範囲、動的生成・共有部品等を扱う必要があり負担が大きい |

初期推奨の操作順: 要素を選択→文字・スタイルを仮変更→即時プレビュー→必要なら自然言語の補足→既存チャットへ適用依頼→コピーの結果を確認→元に反映。

「仮表示」「AIが修正したコピー」「元ファイル」をUIと状態で区別する。仮編集の取り消しとAI編集の取り消しも区別する。AI処理中の追加仮編集、再読み込み、会話切替時に保持・破棄・送信をどう扱うかは未設計。

初版の直接編集対象は静的で単純な文字要素などに限定する案。HTML内の装飾・子要素を壊さないことを優先。現行セレクタは表示中のDOMを示すだけで元ソース位置は未確定。同じクラスの全要素／選択要素1つ、CSS継承、画面幅別の指定をどう保存するかが難所。

## 6. WebView・メモリ・画面領域の方針（提案）

追加機能数より、同時に動かすページ数・保持する履歴／画像／配信データ・常時処理を管理する。

現行コードの事実:

- PreviewManagerは同時に1セッションを保持し、開き直す際に前のプレビューを閉じる。
- アプリUI用とは別の専用子WebViewを使い、プレビュー用profileを指定する。実際のプロセス数・メモリは未測定。
- メニューやダイアログ中のhideは休止・解放ではない。現在の表示制御には明示的な休止処理がない。
- 配信対象ファイルは上限付きでRust側メモリにも保持する。WebView側の画像デコード・DOM・JS等とは別の負担。
- 選択用スクリプトはドラッグ中にページ内要素を走査し、ホバー等でも枠を描き直す。大きいページのCPU負荷も要確認。

採りたい制約:

| 対象 | 推奨する扱い |
| --- | --- |
| ライブページ | プレビューは同時に1つを維持。入力欄・設定パネルごとのWebView追加は避ける |
| 即時プレビュー | 選択要素だけ更新。スライダー等の入力頻度を調整し、毎回フル再読込みしない |
| 履歴 | ページ全体のDOM・画像を毎操作複製せず、変更値の差分を保持する方式を検討 |
| スクリーンショット | 必要な送信・確認時だけ撮影。連続撮影と画像の多重保持を避ける |
| 見た目の比較 | 初版は画像比較／切替表示。2枚のライブページ常駐は採らない案 |
| 非表示・終了 | 短いメニュー操作は非表示、明示的に閉じたら解放。長時間非表示の休止は状態保持・復帰を設計して判断 |
| 画面幅 | 常設の第4ペインを増やさず、簡易操作と必要時の設定パネル。プレビュー拡大の表示切替を検討 |

MicrosoftはWebView2の複数プロセス構成と、不要なインスタンスを増やさない設計を説明している。[性能ガイド](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/performance)・[プロセスモデル](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/process-model)

環境・プロファイル共有による節約は、権限・保存領域の境界を維持できるか確認してから判断する。メイン画面との安易な統合は行わない。プレビュー由来の入力を未信頼データとして扱い、AI送信やファイル保存の権限を直接渡さない。ネイティブWebViewはReactの重ね表示より前面に出るため、近傍入力は単純なDOMポップアップ追加だけでは実現できない。

## 8. 方針の合意と改訂（2026-10-26 追記）

第4〜7節の検討を受け、利用者と以下を合意した。いずれも方針の合意であり、実装・検証は未着手。第7節の段階案はこの節で置き換える。

### 8.1 合意事項

| 項目 | 合意内容 |
| --- | --- |
| 色・サイズ・余白の設定パネル | 初期スコープから外し保留。AIへの依頼で足りる場面が多く、CSS適用範囲・仮表示とAI結果の不一致など負担が大きいため。指示のひな形を強化して補う |
| 文字の仮編集 | 残す。誤字修正など小さく頻繁な作業はAI依頼では割に合わない。対象は子要素を持たない静的なテキスト要素に限定 |
| チャットの扱い | ビジュアル編集中だけ、チャットを右端に畳むドロワー式にする。通常のチャット作業は現行の3ペインのまま |
| ドロワーの実現方式 | プレビューのネイティブWebViewは前面に出るため、重ね表示はしない。開閉時にWebViewを縮めて場所を空け、スライドと影で重なったように見せる。開閉でページを再読込みしない |
| 画面領域の方針 | 通常時に使わない要素で画面を占有しない。使うときだけ出す |
| チャットの汚れ対策 | 表示と送信を分ける（8.3） |
| 近傍のAI依頼 | 第1段は選択付近ではなく、プレビュー直下の固定位置の選択バー。選択の真横に出す案は、効果を見てから判断 |

### 8.2 画面構成の改訂案

現状（スクリーンショット確認）では、プレビューが縦の約6割しかない。開始前の3択・詳細、下部のヒント・選択欄・「細かく指示する」・ファイルの場所が、使用頻度に比べて場所を取っている。

- **開始設定**: 会話方式（今の会話／分岐／新しい会話）は開始前のみ表示する。開始後は1行のステータス（例: 編集中・ファイル名・会話方式）に畳み、会話方式は残して後から確認できるようにする。詳細・ファイルの場所は`⋯`メニューへ移す。反映・取消・終了は使うときだけ見せる。
- **下部領域**: 選択がないときは高さを持たない。選択すると1行の選択バー（選択チップ、指示入力、送信、ひな形を選ぶ「＋」）が現れる。AIの進行状況は選択バーの上に1行で出す。操作ヒントはツールバーのツールチップへ移し、「細かく指示する」の開閉は廃止する。
- **チャット**: 編集中は初期状態で閉じる。承認要求・質問・受理不明・失敗は、折りたたみ中でもバッジとバー上の表示で必ず気づける形にする。承認の代行はしない。
- 縦の使える高さは、現状の約640pxから約850pxへ広がる見込み（目測の概算）。実測は実装後に行う。

### 8.3 チャットの汚れ対策

現行では、送信のたびに`visualSendContext`が参照情報を本文へ追加し、ひな形挿入（`selectionDraft`）は選択要素のJSONを入力欄へ入れる。このため会話にセレクタ・注意書きが積み重なる。

1. **表示と送信を分ける（主体）**: AIへ送る本文は維持し、チャット表示では`VISUAL_CONTEXT_MARK`以降を折りたたみチップ（例: 選択3件・ファイル名）で表示する。選択情報は入力欄の外のチップとして保持し、送信時にだけ本文へ結合する。ひな形が入力欄へ入れるのは短い指示文だけにする。
2. **固定の注意書きは初回と変更時のみ送る（併用）**: 編集可能ファイル、UTF-8、apply_patchの注意などは、会話の最初と内容が変わったときだけ送る。2回目以降は選択セレクタの差分を送る。長い会話でAIが注意書きを忘れないか、実Codexで確認が必要。

AIバックエンド境界の複雑化を避けるため、要約と詳細取得を組み合わせる方式は採らない。

1. **土台（試作確認のみ）**: WebView縮小・復元・アニメーションの小さな試作で、ドロワー方式の実現可否・ちらつきを確認する。メモリ・CPUの詳細計測は、WebViewを1つのまま増やさない限り省略し、不具合の兆候が出たときに行う（2026-10-26 合意。クレジット節約のため）。

## 9. 他社の「会話と成果物」の扱いとの比較、版と「戻す」の方針（2026-10-28 追記）

Web調査（公式ドキュメント中心。確認日 2026-10-28。ChatGPT Canvasは公式本文を取得できず、会話を編集したときの挙動・共有は未確認。Claudeの版履歴UIも公式記事では未確認）と、AgentDockの現状を比較した。

- 他社の共通点: 編集は同じ会話で続く。会話の一手ごとに成果物の版ができ、各版に「確認・差分・復元」がある（v0・Lovable・Cursor・Replit）。復元の前に読み取り専用で過去の版を見られる（Lovable）。復元は、新しい最新版として作る方式（v0）、ファイルだけ戻す方式（Cursor）、会話の文脈ごと戻す方式（Replit）に分かれる。範囲を選んで依頼できる（Claude・ChatGPT）。戻せない外部の副作用は明示する（Lovable・Replit）。
- AgentDockの現状: 同じ会話で編集を続ける（今の会話／分岐／専用）、範囲選択と依頼、編集用コピー・差分・利用者の操作での反映、元の変更の競合検知は同等以上。弱い点は、ターンごとの版の一覧、任意の版へ戻す、過去の版の読み取り専用プレビュー、反映後に元を戻す操作。
- 方針（優先度順）: (1)反映後に元を反映前へ戻す［実装済み・2026-10-28］、(2)版の一覧（送信ごとの前後の保存を、依頼の文と結び付けて表示）、(3)過去の版の読み取り専用プレビュー、(4)任意の版へ戻す（新しい最新版として作る方式。履歴を壊さない）。直接のページ内編集は引き続き保留。AgentDockの強み（元に影響しない、利用者の操作で反映）は保つ。
