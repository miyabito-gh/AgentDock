# 親Codex + サブエージェント方式への移行

状態: 利用者が移行方針と着手を了承。2026-10-24。以下は受入条件を定めた計画で、完了実績ではない。
基準: fbe67ca、タグ baseline/org-engine-2026-10-24。旧版はmasterに保存。新しい開発はfeature/subagent-migration。

## 1. 責任分担
親Codexは計画・分担・順序判断・差し戻し・最終報告を担当。子は委任された作業を行う。AgentDockは通常チャット操作、承認・質問、親子監視、受理不明の抑止、停止確認、保存、差分・利用者操作の取り込みを担当する。
利用者から見た1依頼・1親チャットであり、1turnだけに制限しない。実行中の補足は親へsteer、非実行時は通常送信を使い、受理と反映を区別する。

## 2. 最初の構成
依頼ごとに1つの専用worktreeを用意する。調査は並列、編集は同時1体、検証は編集停止後。これは最初は親への指示であり、厳密な排他制御や子別sandboxと偽らない。
子を作れば専用worktreeが自動でできると仮定しない。組織タスクの上限とCodex側の子数上限を混同しない。モデル禁止等のプロンプト指定を機械的な強制保証と表示しない。

## 3. 段階と受入条件
- D0 文書: 共通AGENTS、Claude補足、README、引き継ぎ、正本の移行追記をコードより先にコミットする。
- U1 モデル表示: 同一チャットの設定更新経路を確認し、選択表示と送信値が一致する。不具合が確認できなければ変更せず根拠を残す。
- U2 画像: 複数画像が受け取れる形式とOSの制約を確認。不対応を成功扱いせず、取得できた画像を扱うか件数を説明する。
- U3 差分: UI・ホストの上限を区別し、取得済み差分の末尾まで閲覧できる。巨大差分で操作が固まらず、省略は明示する。
- U4 外部操作: 設定したエディタでファイル・行、対象worktreeでターミナルを開ける。パスの検証と既存の確認条件を維持し、文字列をシェルコードへ連結しない。
- U5 検索: 名前に加えて作業フォルダ・状態で絞れる。会話横断本文索引は後続段階とし、今回未実装なら明記する。
- S1 新方式: 新規依頼からworktreeと親チャットを作り、子へ分担できる。通常の送信・承認・監視を再利用する。
- S2 継続と復旧: 追加指示、親子の停止、承認待ち、受理不明、再起動後の照合で二重送信・未確認成功がない。
- S3 成果: 依頼ID、親ID、開始コミット、worktree、観測した子、成果・取り込み記録を保存し、旧記録と区別する。既存取り込み処理は組織タスク依存を調査し、必要な部分だけ共通化する。
- L1 退役: 新方式の実機受入後だけ旧方式の新規開始を止める。実行中の旧作業は停止確認と成果回収後、履歴を閲覧専用で残す。自動移行しない。エンジン撤去は最後。

## 4. 保存・ロールバック
設定・認証・通常履歴は継承する。~/.codexをコピーしない。保存形式変更前にアプリ・管理実行の停止を確認し、AgentDock領域だけバックアップする。実行ファイル/ソースを戻すだけではデータは戻らない。旧フォーマットを破壊する変更では復帰手順と読取り互換性を先に定める。

## 5. 確認
ソースのチェックと実機受入を分ける。対象Codex版を実行時に確認し、保存schemaの存在だけで機能を保証しない。
専用のローカルGitリポジトリで分担、追加指示、承認、停止、切断/再起動、差分、取り込みを確認する。会話とモデル利用が発生し、設定・認証は既存環境を使用する。承認代行はしない。実行許可の範囲が未確定なら、この実機工程の前に確認する。
失敗条件を含む関連テスト、cargo check、フロントエンドbuildを変更範囲に応じ実施し、対象コミット・コマンド・結果をHANDOFFへ記録する。
