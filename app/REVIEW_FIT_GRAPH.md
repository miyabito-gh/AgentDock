## 結論（5行以内）

1. G-A は「コード作業を計画→実装→検証で周回させる」仕組みとしてはよくできているが、利用者の主目的（通常業務・目的別の継続チャット）には**ほぼ応えていない**（Git 必須・業務テンプレートなし・同時1件・文書を読む画面なし）。
2. 継続チャットは設計上 G-D（G-B→G-C の後、約20タスク先）にあるが、**既存の通常チャット＋Codex の自動圧縮＋受信済みの使用量（context_window）**を使えば、はるかに近い位置から作れる。
3. Claude Projects との対応表で実装済みなのは「役割スレッド（git）・周回・1ワークフロー内の受渡し・進捗画面・見積り」まで。ゴール・コーディネーター・共有メモリ・ライブラリはすべて設計のみ（概要段階）。
4. 安全側の意図的な違い（提案だけのコーディネーター、承認代行なし、自動マージなし）は妥当。ただし業務利用では確認ブロックと技術用語の多さが負担になる。
5. 順序 U5=(a) は副目的（組織実行）を主目的より先に置いている。継続チャットの最小版を前倒しする再判断を勧める。

## 推奨する次の一手（最大3つ）

1. **既存チャットで「長い目的別チャット」を実機で試す（実装なし）**。理由: Codex は自動圧縮を行う（`ThreadOpsDialogs.tsx:291` の文言が前提にしている）ため、引き継ぎ機能なしでもどこまで使えるかが分からないまま G-D を設計すると過剰になり得る。議事録用チャットを1本立てて数十往復し、圧縮の発生・品質の落ち方・待ち時間を記録する（利用者メモ「再設計の前に今の実装を試す」とも一致）。
2. **「継続チャット 最小版」を G-B より前に入れる（U5 の再判断＝要判断）**。理由: 主目的に直結し、案件メモ・ライブラリがなくても成立する。中身は ①チャット単位の「目的メモ」（利用者が書く固定文。送信時に資料として添える）、②文脈の使用率の表示（`TokenUsage.context_window` は受信済みで画面に出していないだけ、`backend.rs:103`）、③利用者が押す／次の送信で行う「新しい thread へ引き継ぎ」（目的メモ＋直近数往復を決定的に組立て、表示は1本につなぐ）。自動送信なし・自動 resume なしで既存合意に収まる。見込み 4〜6 タスク。
3. **G-B は「folder＋議事録テンプレート1本＋文書の表示」に絞って先に出す**。理由: 業務での周回の価値を最小コストで確かめられる。今は出力が JSON のまま gate カードの `<pre>` に出るだけで（`OrgPane.tsx:513`）、文書として読めない。調査メモ・メール下書き・入口②③は実際に使ってから。

## 1. 利用者の目的との適合

### (a) 業務（Git 以外）で今日使えるか — ×

- 【事実】開始には Git リポジトリでコミットが1つ以上必要（`host/org/mod.rs:249-254`）。folder のテンプレートは「まだ対応していません」で選べない（`host/org/graphs.rs:99`、モックの `folder-draft`）。
- 【事実】組込みテンプレートは `standard`・`quality-loop` の2つで、どちらも Git とコード作業前提（`templates.rs`）。
- 【事実】開始の入力は依頼文・作業フォルダ・並列数・turn 上限・テンプレートだけで、**添付（会議の文字起こし等）を渡す入口がない**（`OrgDialogs.tsx:75` の `StartOrgArgs`）。依頼文に貼れる長さの上限は未確認。
- 【事実】同時に動かせるワークフローは1件（`mod.rs:267-268`）。
- 【事実】成果物の閲覧は「チャットを見る」かブランチ・差分の確認。スロットの値を文書として読む画面はなく、gate の「見せる内容」は JSON の整形表示（`OrgPane.tsx:510-514`）。
- 【推測】回避策として、文書用フォルダを `git init` し `writer`（`roledef.rs:287`）と `verifier` で自作グラフを書けば動く可能性はあるが、成果は `agentdock/org/...` ブランチのコミットになり、取り込みは利用者の手作業。業務利用者向けとは言えない。
- 足りない点: folder の置き場、業務テンプレート、入力ファイル、文書の表示・保存。
- 最小の追加: G-B を folder＋議事録1本＋文書表示（Markdown 表示は既存の react-markdown を使える）に絞る。

### (b) 継続チャット（自動ロールオーバー）への距離 — ×（G-A 内）／ただし実距離は短い

- 【事実】G-A には継続チャットに関わる実装はない。設計は §5.2 にあり、段階は G-D（依存 G-A→G-B→G-C→G-D、§1）。G-B 約7、G-C 6〜8、G-D 6〜8 タスクの見込み（§14.2）＝約20タスク先。
- 【事実】既存の資産: 通常チャット、手動の圧縮（#7、`ThreadOpsDialogs.tsx`）、編集して再送・fork（`ResendDialog`）、`TokenUsage { last_total, thread_total, context_window }` の受信（`backend.rs:103`、「画面には出さない」）。org 以外では使用率を表示していない。
- 【推測】Codex は文脈が上限に近づくと自動圧縮するので、「利用者がコンテキスト量を意識しない」体験の半分は既に得られている可能性がある。足りないのは「目的の固定（圧縮で目的・様式が薄れない）」「長くなったときの明示的な引き継ぎ」「残量の見える化」。どれも案件メモ・ライブラリなしで作れる。
- 設計 §5.2 との関係: §5.2 の引き継ぎ資料は「採用済みメモ・ライブラリ一覧・直近の原文・ゴール」。メモとライブラリを「利用者が書く目的メモ」に置き換えれば G-C を待たずに成立する。後で G-C が来たら目的メモ→案件のゴール・メモへ移す（§5.3 の「邪魔にならない約束」と同じ考え方で、保存形式に `purposeNote` を1つ足すだけ）。
- 最小の追加: 推奨2（目的メモ・使用率表示・利用者操作での引き継ぎ）。

### (c) 「毎回チャットを作る手間」は減ったか — ×

- 【事実】役割チャットは左一覧から隠している（`orgHidden.ts`）。一覧が役割チャットで埋まることはない（良い点）。
- 【事実】ただしワークフローは依頼ごとに新規で、完了まで次を始められない（`OrgPane.tsx:334` の「新しいワークフローを開始…」は完了時のみ有効）。続きの依頼（入口③）は G-B。
- 業務の「議事録チャットを使い続ける」には寄与しない。G-A は手間を減らす機能ではなく、品質を周回で上げる機能。

### 順序（U5=(a)）の妥当性

- 主目的（継続チャット）が最後、副目的（組織実行の拡張）が先という並びになっている。利用者メモでも「組織エンジンは二次的」とされている。U5 の推奨理由「メモとライブラリが先にあると引き継ぎ資料が作れる」は、目的メモで代用できるので決定的ではない。
- **要判断（U5 の再判断）**: (a) 現行どおり G-B→G-C→G-D ／ (b) 継続チャット最小版（推奨2）→ G-B 縮小版（推奨3）→ G-C → G-D（窓口の提案・承認カード）／ (c) 継続チャット最小版だけ先に出し、組織実行の拡張は実機の結果を見て決める。設計担当としては (b) を勧める。

### Projects にあって設計に欠けている（または弱い）概念【推測を含む】

1. **プロジェクト単位の恒常指示**（文体・宛先・社内用語・議事録の様式）。案件の「ゴール」はあるが、毎回の送信に効く固定指示としての位置づけがない。業務では最重要。推奨2の目的メモがこれに当たる。
2. **知識ファイルの本文を参照する前提**。§4.3 はライブラリの一覧だけを渡し、本文は役割がパスから読む。Codex が docx・pdf・xlsx をどこまで読めるかは未確認（実機確認が要る）。
3. **1つのプロジェクトで複数の作業を同時に**。今は全体で同時1件。G-C で案件を作っても、同時1件のままでは「並列スレッド」にならない。
4. **会話からの自然な依頼と進捗の質問**。G-D の範囲。窓口がない間は、開始ダイアログに依頼を書き直す必要がある。
5. **成果物を文書として見る・コピーする**。スロットの文書を表示する画面が設計（§11）にない（G-B の「保存…」だけ）。

### 意図的に違う点の妥当性

- コーディネーターは提案だけ・実行は承認カード（§2 末尾）、gate を自動で決めない、承認代行なし、自動マージなし、自動 resume なし: 既存合意（正本 §3.15、CLAUDE.md の守ること）に沿っており**妥当**。
- メモは全て利用者が採用（U7=(a)）: 安全だが業務では提案が溜まりやすい。採用画面を「まとめて採用」中心にする前提で妥当（G-C の詳細設計で、提案の数を役割ごとに上限で抑えることを入れたい）。
- 引き継ぎは利用者の送信時だけ（§5.2）: 合意（無条件再送なし・監視目的の送信なし）に沿い妥当。体験上も「次に送ったら新しい会話に切り替わる」で十分自然。

## 4. UI・操作の妥当性（コードとモックから。画面は見ていない）

### 良い点【事実】

- 選ぶ・開くだけでは何も送らない、状態は文字＋アイコン、未取得を0や完了で代用しない、という原則が一貫している。
- 周回上限カードの2択（もう1周／この結果で受け入れる）は、自動では進まないことが明確。
- 見積りに「turn 上限を超える可能性」を出している（`org.ts:115`）。
