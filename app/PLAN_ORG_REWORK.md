# 組織実行 改修計画（2026-10-19 案 v0.1）

目的: 組織実行を「何をしているか見えて、途中で介入でき、止まっても再開でき、成果がそのまま見える」ものにする。業務利用（議事録・調査・資料・メール下書き）を主用途にする。
前提: 下記の問題点はユーザー報告とコード調査（DEFERRED.md の2026-10-19項）に基づく。**コードの詳細は未精査**。各段階の冒頭の設計で確定する。

## 1. 問題点の整理（これまでの指摘）

|#|問題|由来|
|---|---|---|
|1|承認待ち・要対応のまま回答できず進まない（原因は未確認。AlreadyResolved の黙殺、待ちが組織画面外で見えない、タスクに待機理由が出ない）|報告|
|2|利用上限で止まると再開手段がない（再開・やり直しの対象外）。履歴照合で上限が Failed になり得る|報告|
|3|途中で補足・修正の指示を送れない（Q9で手入力不可。手動切替は自動で進まず成果も取込まれない）|質問|
|4|成果物が見えない。別ブランチを開いて取り込む必要がある|質問|
|5|Git必須。業務フォルダ（Gitなし）で使えない|調査|
|6|何をしているか分からない（進行・待機理由・誰が何をしているか）|報告|
|7|「空き容量が足りません（空き0）」の一過性エラー|報告|

## 2. 方針（4つ）

1. **見える**: 進行を時系列で見せ、待機理由（承認待ち／質問／上限停止／停滞／接続断）をタスクに明示する。組織画面の外でも気づける。
2. **介入できる**: 承認・質問に回答でき、実行中の役割／次のタスクへ指示を挟め、一時停止・再開・やり直し・スキップができる。
3. **止まらない／止まっても戻れる**: 上限停止・失敗を利用者の1操作で新しい試行として再開できる。通信断を done/failed にしない合意は維持。
4. **成果が手元に出る**: 成果物パネルで中身（文書はプレビュー、コードは差分）を見て、ボタンで作業フォルダへ取り込む。Gitなしの業務モードを持つ。

守る合意（変えない）: エンジンはCodexの承認要求に代行応答しない／自動再送しない／自動マージしない／停止未確認のまま削除しない／~/.codex無断変更なし。介入は**利用者の操作として**行う。

## 3. 段階と内容

### 段階0: 診断（小）
- 空き容量取得の診断ログ（パス・値。挙動は変えない）。取得値0かつ必要量が正のときの1回再取得を検討。
- 承認カード無反応の再現手順の確定（App Server再接続後か、pending欠落か）。`adapter.rs` の AlreadyResolved 黙殺を「取得不能」と表示する修正は段階1に含める。

### 段階1: 止まらない・答えられる（最優先）
- R1 承認・質問: 待ちをタスクの待機理由に反映、組織画面外（左一覧の行・ドック・通知）にも件数表示、無反応時は「取得不能」と原因表示。
- R2 上限停止・失敗の再開: 上限停止タスクを利用者1操作で新試行として再送（回数は設定の上限内）。履歴照合で上限分類を取り込み、分類不能は「失敗」でなく「要対応」。失敗タスクの「やり直す」。
- R3 手動切替後の成果取込み: turn終了と最終回答を読んで成果物を取り込める経路。
- 設計1回（Opus）→実装→検証。実機確認項目: 承認に答えて進む／上限停止から再開／手動切替から完了。

### 段階2: 見える・介入できる
- R4 進行タイムライン: ワークフロー画面に「誰が・何を・いま何の状態か・待機理由・経過時間」を一覧。イベントログ（events.jsonl）を人間向けに整形して表示。
- R5 介入: 役割チャットへの割り込み指示（エンジン管理下のまま1回挟む。送信は利用者操作・履歴に残る）、ワークフロー単位の追加指示（次に走るタスクへ）、一時停止／再開／スキップ／差し戻し。
- 設計1回（Opus、段階1の結果を反映）。Q9「手入力不可」は変更になるため、正本§3.15と DESIGN_ORG を版更新する。

### 段階3: 成果が見える・取り込める
- R6 成果物パネル: Workerのコミット／追加ファイル一覧、文書（md・txt・docx等はプレビュー可能な範囲）、コードは差分。
- R7 「取り込む」: 確認つきで作業フォルダへ反映（Gitを意識させない）。未コミット変更との衝突は止めて案内。自動マージはしない。

### 段階4: Gitなしの業務モード
- R8 worktreeを使わず、出力専用フォルダ（既定 `%LOCALAPPDATA%\com.agentdock.app\` 配下または利用者指定）にファイルを書く。Gitなしフォルダでも開始可。並行Workerの衝突回避は出力ファイル名の割り当てで行う。
- 役割定義（標準 Planner/Worker/Reviewer ＋ 業務向け writer/verifier）を業務テンプレートに整理（議事録／調査／資料／メール下書き）。
- 設計1回（Opus）。Git前提の開始時チェック（`2845519`）を外す条件を設計で確定。

### 段階5: 目的別の継続チャットとの統合
- 継続チャット（C1〜C6、実装済み）を窓口にして、必要時に組織ワークフローを起動できる形を検討（窓口チャット設計の再開）。実機確認の結果を見て判断。

## 4. 進め方・コスト
- 各段階: 設計（Opus 1回）→実装（Sonnet）→検証（Sonnet、最大3回ループ）→コミット。レビュー（R）は段階1と段階2の後に各1回（状態遷移・停止確認・合意違反が絡むため）。
- 段階0は今すぐ着手可。段階1→2は順番、段階3は段階1と並行可（触るファイルが別）、段階4は段階3の後。
- 実機確認はユーザー。段階ごとに `LIVE_CHECK_*.md` を作る。プッシュ・NSIS・マージは指示があったときだけ。

## 5. 決めてほしい点（推奨を先頭に）
1. 着手順: 段階0→1→2→3→4（推奨）／Gitなしモード（段階4）を前倒し。
2. 介入の範囲（段階2）: 役割チャットへの割り込み＋ワークフロー追加指示の両方（推奨）／役割チャットのみ。
3. 業務モードの出力先: 既定フォルダ＋利用者が指定可（推奨）／利用者が毎回指定。

## 6. 決定（2026-10-19 ユーザー）
- 実装範囲は**段階3まで**。段階4（Gitなしの業務モード）・5は今回やらない（設計案のみ保留）。
- 追加（最初に実行）:
  - **入口: 依頼整理フェーズ** — 最初の画面でいきなり依頼を受けず、会話しながら依頼内容を固める。固まった内容を計画（Planner）への依頼として確定してから開始する。設計: `app/DESIGN_ORG_INTAKE.md`。
  - **Gitでないフォルダの扱い** — 指定フォルダがGitでない場合、確認のうえ `git init`（＋初回コミット）して使えるようにする（開始時チェックを「断る」から「作成を提案」に変更）。
  - **アプリ上からのプッシュ** — 成果物に問題なければ、取り込み後にアプリからプッシュ。利用者の明示操作・確認つき・force禁止・自動プッシュなし。
- 順序: 段階0（診断）∥ 設計（段階1・入口）→ 段階1実装 → 入口実装 → 段階2設計→実装 → 段階3設計→実装（取り込む＋プッシュ）。DEFERRED等の記録は随時。
