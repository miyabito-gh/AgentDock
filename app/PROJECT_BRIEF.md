# AgentDock：Claude Projects 用ブリーフ（コーディネーターへの最初の指示）

作成: 2026-10-17。Claude の再設計版 Projects（Claude Code、ベータ）のコーディネーター・チャットに貼る、または最初に読ませるための文書。

## ゴール

AgentDock（Windows 11 上で Codex を使う個人用クライアント）の**組織実行**を育て、次を実現する。
1. 制御の流れを**グラフ定義**（ノード＝役割／決定的処理／人間の承認ゲート／ルーター、エッジ＝通常・条件つき・最大周回数つきフィードバック）で表し、「計画→実行→検証を複数回回して品質を上げる」を動かす。
2. 役割を標準3つ（Planner・Worker・Reviewer）以外にも増やせる。
3. Git 以外（議事録・文書・調査など）の成果物でも使える。
4. 利用者が口を出せる（再計画の理由、実行中の追加指示＝承認カード経由、完了後の続き）。
5. 将来：プロジェクト（ゴール・共有メモリ・ライブラリ）とコーディネーター・チャット、目的別の継続チャット（1つのチャットを使い続け、長くなったら裏で自動引き継ぎ）。

## 守ること（再質問しない合意。CLAUDE.md より）

- 既存の `~/.codex` の設定・認証を無断で変更・コピーしない。
- 組織実行は、利用者が開始したワークフローの ready 状態のタスクだけを送信し、Codex の承認要求には応答しない。終了・通信断を cancelled／failed／completed に変換しない。受理不明で再送しない。監視目的で resume しない（resume は利用者の「再開」操作の中だけ）。自動マージしない。
- 保持期限なし・容量不足で自動削除しない。通信断・取得不能を done・failed に変換しない。未確認の操作を成功表示しない。
- 利用者テキストはプロンプトに「利用者の指示」として区切って渡し、権限を広げない。利用枠の上限（周回×役割）で必ず止まる。

## 進め方

- 設計→実装→検証の流れ：設計判断は設計担当（Opus 相当）、実装は実装担当、検証は検証担当が受入条件と差分を照合。不具合は同じ担当に戻して直す（最大3回）。
- 確認は `cargo check`・`tsc --noEmit`・変更したモジュールに限ったテスト。テスト一式は流さない。画面のテストは書かない。
- **実機確認（実際の Codex・画面操作）は利用者が Windows 11 の PowerShell で行う**。クラウドの作業では実機確認を前提にしない。Windows 固有（Tauri、Windows sandbox、Codex 0.162.1）の確認は、手順書を作って利用者に渡す。
- 新しいネイティブ依存は足さない。既存ファイルの改行コード（CRLF／LF）を混在させない。
- ユーザーへの確認は、細目ごとにせず、選択式（推奨を先頭）でまとめて聞く。

## 最初にやってほしいこと

1. `app/DESIGN_ORG_GRAPH.md` を読み、最初の MVP（周回して品質を上げる＋既存テンプレートの回帰なし）の実装タスクに分解して、利用者に確認する。
2. 利用者判断が要る点（設計書末尾の選択式）が残っていれば、先にまとめて聞く。
3. 実装は、作業ごとにブランチを切り、`cargo check`・テストを通してから報告する。マージは利用者の承認後。
